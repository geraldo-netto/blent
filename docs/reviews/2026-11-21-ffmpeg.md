# FFmpeg measurements, 2026-11-21–22

T1670 examines the bundled FFmpeg 6.1.6 on an AMD Ryzen 9 7945HX. The active display, GUI and tablet were left running. Final measurements began with no Cargo/rustc process present; this was still a working desktop, without fixed affinity, governor changes or cache eviction.

The permanent benchmark generated finite BT.709 limited-range H.264 test clips. Its decoder retains the production scaling, color conversion, padding and YUV420 output recipe. All variants produced identical raw-byte hashes within each resolution/sweep. This covers these synthetic inputs, not every color format or real camera.

## Results

Each table cell is a median of three runs. Throughput observations decode 120 pictures; the paced runs admit 60 pictures at 30 FPS, waiting for each complete output before its successor. Steady picture latency pools 177 samples per resolution/worker count, excluding the first picture of each run. It measures encoded-picture admission to full raw stdout delivery, including Python scheduling and copies; it excludes camera capture, tablet encoding, transport, Rust transforms and webcam consumers.

Two filter workers reduced the finite throughput wall time by approximately 37–38% at all three sizes. The paced 1080p median fell from 11.68 to 7.68 ms, but CPU rose about 18% and p95 worsened from 13.83 to 15.21 ms in this run. At 720p, the median fell from 8.30 to 4.76 ms with about 1% more child CPU. First-picture and tail values vary across runs; neither throughput nor these paced medians establish a guaranteed live-camera or tail-latency improvement.

T1671 carries the bounded 1–4 worker setting, with 2 selected as a modest default and 1 retained as the low-worker choice. Four workers are available for users who prefer their measured tradeoff. Decoder and raw-output encoder threads stay at 1; no frame-threading queue is enabled. T1671 is implemented and verified: 40 common camera tests, 165 host camera tests and 263 GUI unit/integration tests pass. All four maintained production methods have 100% executable-line coverage; 79 examined Rust functions have complexity ≤9. Five new assertions failed before implementation. The single-picture/no-successor regression passes at all four worker counts. [T1671 evidence](artifacts/2026-11-21-open-items/t1671.json) records scope and native limits. The change is source-only and is not installed into active sessions.

Increasing the stdout pipe from 64 KiB to 256 KiB or 1 MiB substantially reduced read calls and voluntary context switches, but gave no consistent meaningful wall-time or CPU improvement. At 1080p, 120-picture wall medians were 1118.6 / 1116.4 / 1122.0 ms, despite read counts of 5763 / 1625 / 843. Retain the current pipe size. A larger pipe also admits more buffering; these measurements do not qualify its delayed-consumer freshness behavior. T1590 retains the separate relay/speaker allocation work and integrated measurement obligation.

Four VAAPI help probes were each executed 20 times without initializing an encoder or opening a GPU. Warm medians were 6.49 ms (H.264), 3.40 ms (HEVC), 3.32 ms (VP9) and 3.31 ms (AV1). These isolated costs alone did not justify caching. The follow-up startup attribution below retains fresh probing. Any future cache must identify the selected wrapper, underlying binary and dependencies correctly.

The existing display path already feeds tagged BT.709 NV12 to its selected hardware encoder. No display codec, rate-control, quality or bundled-library default changed in this investigation. No sustained GPU codec comparison was run. The later startup-only experiment below used private synthetic input while the active display remained running. T1577 retains host rotate/mirror measurements; FFmpeg measurements do not resolve that separate Rust work.

## Reproduce and ownership

```sh
python3 scripts/benchmarks/ffmpeg-camera-pipe.py --ffmpeg /path/to/ffmpeg --sweep pipes --output pipes.json
python3 scripts/benchmarks/ffmpeg-camera-pipe.py --ffmpeg /path/to/ffmpeg --sweep filter-threads --output filters.json
python3 scripts/benchmarks/ffmpeg-camera-pipe.py --ffmpeg /path/to/ffmpeg --sweep latency --frames 60 --output latency.json
```

Each throughput observation owns one child, private encoded clip, stderr file and bounded raw consumer buffer. Each paced observation admits one picture at a time; generated input is capped at 64 MiB, returned raw frames at 1920×1080×3/2 bytes, with temporary asyncio staging/copy storage. Completed frames are discarded after hashing. Normal completion waits for the original child. A paced protocol failure cancels admission, kills that original child, drains its stdout and waits before releasing temporary resources. No task or child is intentionally detached. These boundaries were reviewed; they are not an unrestricted proof of FFmpeg memory safety. Native peak RSS and additional worker-stack memory were not measured.

The benchmark CLI bounds frames to 30–300 and repeats to 1–7; each run owns one clip at a time and fixed three-resolution/three-variant sweeps. The three-second picture-output deadline enforces the no-successor protocol experiment, not a total runtime limit. All 14 benchmark functions measure at complexity ≤9 using the project Python AST 3.12 checker. Benchmarks are exempt from production per-function coverage under AGENTS.md.

[Summary, provenance and complexity](artifacts/2026-11-21-open-items/t1670.json) include executable/script hashes. [Raw observations](artifacts/2026-11-21-open-items/ffmpeg/) retain the 81 final decoder observations, 80 capability probes and preliminary runs. Final throughput sweeps use unbuffered readinto and hash all bytes; the paced sweep uses asyncio readexactly and records its picture timings. Do not compare their read counters as equivalent syscalls. Preliminary paced results overlapped later compiler activity and are retained only as preliminary evidence.

## T1674 — native startup attribution

The opt-in `capture::cli_encoder::startup_profile::t1674_native_startup_probe_attribution` benchmark uses the production capability probe, encoder argument builder and packetizer. It feeds one synthetic NV12 checkerboard and measures through the complete first IDR packet while stdin remains open. Ten observations per codec/size alternate codec order: 60 observations total, with no compiler running. This measures the private encoder-start portion; it excludes viewer authentication, geometry negotiation, capture acquisition, transport and tablet rendering. The host harness is a debug build, FFmpeg is the bundled native release binary, and the ordinary desktop remains active.

| Encoder | Size | Median probe (ms) | Median start to first packet, including probe (ms) | Median probe fraction |
| --- | --- | --- | --- | --- |
| H.264 VAAPI | 640x400 | 5.43 | 32.48 | 16.62% |
| H.264 VAAPI | 1280x800 | 4.41 | 34.74 | 13.26% |
| H.264 VAAPI | 1920x1080 | 4.44 | 37.84 | 12.32% |
| HEVC VAAPI | 640x400 | 4.93 | 38.51 | 11.85% |
| HEVC VAAPI | 1280x800 | 4.40 | 42.83 | 10.43% |
| HEVC VAAPI | 1920x1080 | 4.40 | 50.74 | 9.14% |

Retain fresh capability probing. Its fraction of this short startup portion is visible, but the median saving ceiling is only 4–5 ms once per start, before identity lookup/invalidation costs. It offers no steady-frame improvement. This does not justify another runtime cache on the measured machine; no claim is made about slower machines or complete viewer startup. The largest individual probe was 10.41 ms.

Each observation owns one FFmpeg child and GPU encoder context, one bounded input frame and the production packet reader. After success or protocol failure, the original child is killed and waited before resources are released. No installed session is stopped or modified. All six benchmark functions have complexity ≤9; benchmark coverage is exempt under project policy. [Raw observations and provenance](artifacts/2026-11-21-open-items/t1674.json), [native log](artifacts/2026-11-21-open-items/t1674-native.log.gz).

To reproduce, put the intended FFmpeg launcher first on PATH, build the host test binary, then run its exact `capture::cli_encoder::startup_profile::t1674_native_startup_probe_attribution` test with `--ignored --nocapture`. It uses `/dev/dri/renderD128` and requires H.264/HEVC VAAPI support; failure is reported, never counted as a measurement.
