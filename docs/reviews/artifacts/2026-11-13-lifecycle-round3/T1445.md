# T1445 — bind X11 registration to each native creation

X11 payload construction now issues a distinct creation name before cursor preparation or native construction. The constructor, cursor policy and mapper share that immutable identity; remapping the same payload retains it, while detach/reattach issues another. A delayed old registration can no longer satisfy a replacement's expected kinds merely because its instance base name matches. Instance product IDs retain their checked 0..4095 range. KWin names remain stable and bypass the issuer entirely because KWin persists settings by vendor/product/name.

The authoritative issuer is constant-sized process-owned state: one mutex, an optional 128-bit namespace supplied through the existing Entropy/system_entropy contract, and one checked 64-bit sequence. Entropy failure issues nothing and leaves initialization retryable. Poison and counter exhaustion fail before native effects; the sequence never wraps. Across process restarts, namespace separation assumes independent CSPRNG output and is probabilistic, not an absolute collision guarantee. Generated names are ASCII and at most 69 bytes, within the 80-byte uinput field.

Name allocations and immutable copies are bounded per admitted payload; the issuer retains no history. The mapper future is cut off before local names are dropped. Original command ownership retains copied arguments and the T1439 native payload independently through acknowledgment/retirement. No parent/task cycle or new background worker is introduced. Existing pen-tool suffix recognition remains unchanged; this adds no stylus capability.

The permanent regression `host/tests/input_mapping/identity.rs::t1445_replacement_ignores_old_registration_and_maps_new_creation_without_watch_event` failed before production edits against the frozen e4bcb6f1 library. `T1445-red.log` and provenance retain that failure. It creates two actual backend payloads through private uinput interception, leaves the old server registration visible after replacement construction, publishes the new registration without changing tablet/mode/card state, and checks automatic mapping plus stale/foreign rejection. Its faulty-control branch proves the new registration is reachable and settles both fake payloads before asserting the original failure.

Final verification passes 44/44 tests: 8 mapping integration, 3 OSK integration, 7 constructor/identity integration, 13 Linux lifetime/creation unit tests and 13 mapping unit tests. The bounded property control checks 49,152 distinct names: 4096 instances × four independent namespace/sequence boundary combinations × three device kinds. Other controls cover retryable entropy failure, single initialization, KWin bypass, poison, repeated overflow rejection and 256 concurrently issued unique stamps. The shared uinput fixture now logs actual setup names; all four fixture-consuming test groups are included in this cohort.

`T1445-coverage.json` records 12/12 changed production functions at least 80% executable-line coverage, 11 at 100%, minimum 90.91%. Four exact instrumented objects and 35 matching profiles produced the source-relative LCOV. `T1445-complexity.json` measures 135 containing functions across nine changed production/test/fixture files, maximum 9; that file-wide count includes unchanged functions. Toolchain: Rust 1.100.0/LLVM 23.1.5, cargo-llvm-cov 0.8.7 and repository syn 2.0.119/C tree-sitter complexity tooling. Source/object hashes are retained; generated binaries/profiles and absolute cache manifests remain external.

Reproduce using the same Cargo build/cohort commands as T1439, adding the normal `input::mapping::` library filter. The additional creation unit tests are under `input::linux::creation_identity::tests` and run in the existing Linux filter.

Limits: this is hosted protocol/ownership evidence, not live Xorg/KWin/tablet acceptance. Private fixtures verify marker 497 before constructors and use isolated commands/sysfs/uinput files; children and fake devices settle. T1446 separately addresses numeric-ID reuse between helper connections; creation-name uniqueness alone does not resolve that command-addressing boundary. Nor is there a claim against arbitrary same-helper registry changes between lookup and effect. Existing blocked and declined platform/input work remains unchanged.
