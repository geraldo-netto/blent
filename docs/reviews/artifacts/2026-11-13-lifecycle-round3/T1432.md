# T1432: original control worker process-exit fence

Control workers now reserve a process retirement observation before native thread
creation. Runtime shutdown closes process admission, closes the shared configuration
executor, and drains original native proofs while the runtime remains alive. The
shared configuration pool stays reusable during normal operation; shutdown removes
its sender and transfers its workers to retained retirement, preventing its static
owner from keeping idle registered threads alive forever.

The process observation grant is 12,420: 4,096 session + 4,096 route + 4,096 input
+ 4 activity + 64 shared control + 64 shared configuration observations. Public
custom control pools consume this same overall bound; they are not collectively
limited to 64. The permanent exhaustion/reuse regression retains old observations
and exercises the exact grant.

## Permanent regressions and order

- `host/tests/control_exit.rs`: the original held worker/TLS regression failed
  before production edits (`T1432-red.log`): runtime returned before the original
  native thread/TLS destructor exited. Its eight child scenarios cover normal,
  error, cancelled and panic workflows, each with native-body and TLS gates.
- `host/tests/control_exit/config.rs`: six shared-store scenarios cover normal,
  error, panic, held TLS destruction, active work plus queued cancellation, and
  invalid configured capacity. Added before production edits; the first case
  failed because the shared executor reopened after cutoff
  (`T1432-config-red.log`). Retained Store owners cannot reopen admission; active
  work preserves its outcome, queued work is discarded, and static ownership does
  not deadlock process exit.
- Draft review found queued opaque request destruction had moved outside panic
  containment. The permanent queued-destructor-panic/sibling-progress regression
  failed before correcting that draft (`T1432-discard-red.log`). Discard now runs
  inside the same unwind boundary as execution.
- Draft review found a held shared-initialization mutex could delay process cutoff.
  The permanent held-gate regression failed before reordering shutdown
  (`T1432-gate-red.log`). Process admission now closes before acquiring the shared
  executor gate. This fixture holds the actual gate; it does not claim to stall
  the operating system's thread constructor.

All four integration tests passed after the change (`T1432-green.log`). The final
instrumented run passed 52/52 selected Rust tests (`T1432-coverage.log`): process
retirement 3, control workers 3, configuration jobs 9, camera control 10, audio
control 9, persistence 4, daemon shutdown 2, control exit 4, activity exit 2,
process exit 2, runtime exit 2 and WiFi exit 2. The eight held-control and six
shared-store child scenarios are executions inside those integration tests, not
14 additional Rust tests. This is a focused cohort, not a whole-suite result.

## Ownership audit and limits

The registry serializes cutoff with worker admission and retains the exact native
thread proof before spawning. Existing worker retirement still joins the original
thread through TLS destruction. Logical completion and caller loss do not release
that proof. Capacity is released only through the original admission lifetime.

The shared executor gate owns initialization and its cached result. Shutdown closes
process admission first, so an initializer delayed at that gate cannot admit new
workers afterward. The gate then ensures any already-admitted initializer publishes
its outcome before shared shutdown examines it. Queue admission and closure are
serialized separately. Rejected opaque requests and retired workers are dropped
outside the queue lock; no blocking join occurs under either lock. Queued discard
and execution share panic containment. Already-started work retains its original
result and cleanup sponsor.

The static executor retains bounded metadata after shutdown, but no queue sender
or worker owner. Existing WiFi exit cleanup has no configuration Store dependency;
its targeted exit regressions pass. Dedicated caller-owned executors retain their
normal drop/close obligation. Runtime-entry workflows must stop/drop their owned
resources before returning. Eventual drain still requires original native/backend
work to finish; this change does not promise forced interruption of arbitrary I/O.

All held-work fixtures use owned threads, channels and child processes, with gate
release and join before final assertions. No live service, ADB endpoint, tablet,
media device or GUI was changed. The separate GUI entry integration gap is T1435;
registering workers alone does not add a drain to an entry point that never calls
it.
