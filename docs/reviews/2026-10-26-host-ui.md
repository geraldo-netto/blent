Status, 2026-10-27: owner accepted the revised tablet-resource workspace and
instructed that it be committed and implemented. The desktop, compact,
first-connection and permission-waiting SVGs define the approved direction.
Implementation proceeds under T1272 (independent contracts) and T1273 (native UI),
with native Windows validation tracked separately under T1271. The earlier

## Evidence and scope

The running installed application was inspected at 440×760 without operating
any device or service control. [Before image](artifacts/2026-10-26-t1268/before.png).
Video/GPU tuning occupied the initial screen. Pairing controls lived in a separate
USB connection tab, and operation results shared weak footer text. The original
[layout.svg](artifacts/2026-10-26-t1268/layout.svg) retained seven peer destinations,
a large service Stop action and a display-assignment focus. It is superseded.

Source inspection covers gui/src/main.rs, connection_settings.rs,
camera_settings.rs, audio_settings.rs, media_target_settings.rs, status_poll/,
platform/ and the independent common camera/audio/connection contracts. The
current uncommitted draft implements Overview/navigation improvements, individual
display-assignment names and scoped, bounded feedback; it does not supply a
complete cross-resource device model. The installed window was not replaced.

Blent already exposes display/input, a selected front/rear camera, microphone
input and speaker output. Camera and audio have their own targets, controllers,
consent and lifetimes. A tablet can serve media without sharing a display.
Device identity, connection state, admitted display assignment and actual resource
activity are different facts. A daemon PID or display assignment cannot stand in
for all of them. Labels and model names are presentation, never authority.

## Research and implications

The owner explicitly authorized online guideline research. Only text/reference
pages were consulted; no tool, font, image, framework or package was downloaded.
The following are primary design sources, not measurements of Blent usability.

| Source | Relevant guidance | Proposed application to Blent |
| --- | --- | --- |
| [KDE: Simple by default](https://develop.kde.org/hig/simple_by_default/) | Make the first useful action obvious; keep common controls visible; reduce irrelevant choices. | First connection has a clear Connect action. The selected tablet exposes its useful resources without requiring a tour of settings tabs. |
| [KDE: Powerful when needed](https://develop.kde.org/hig/powerful_when_needed/) | Retain expert workflows; reveal optional detail with meaningful labels instead of a generic Advanced category. | Use Display settings, Camera image, Audio processing, Encoding and performance, and Connection details as descriptive entry points. Preserve existing capacity choices and tuning. |
| [KDE: Layout and navigation](https://develop.kde.org/hig/layout_and_nav/) | Placement and proximity convey grouping; navigation should support the task. | Group device selection separately from the selected device's resource controls. Keep resource state, action and recovery together. |
| [Apple HIG: Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls) | Reveal detail when relevant and place its disclosure near the affected content. | Each resource opens its own configuration; the home view avoids a dense configuration form. This is design guidance, not authorization for a macOS port. |
| [Microsoft: Commanding basics](https://learn.microsoft.com/en-us/windows/apps/design/basics/commanding-basics) | Frequent commands belong close to the affected content; choose controls by task and integrate useful feedback. | Per-resource Start/Stop controls stay visible. Secondary connection/settings commands have clear scope. Permission requests and errors remain beside that resource. |
| [Microsoft: Navigation basics](https://learn.microsoft.com/en-us/windows/apps/design/basics/navigation-basics) | Keep paths clear and avoid unnecessary navigation overhead. | One tablet workspace replaces seven equally prominent page choices. |
| [Google: Material 3 adaptive list-detail](https://developer.android.com/develop/adaptive-apps/guides/list-detail) | Related list/detail content can be adjacent on wide windows and use one pane in compact windows. | Wide view uses tablet list plus resource workspace. Compact view uses tablet selection plus a single-column resource list. No Compose or Material runtime dependency is proposed for egui. |
| [GNOME: Adaptive design](https://developer.gnome.org/hig/guidelines/adaptive.html) | Design from constrained windows and preserve functionality when layout changes. | Compact is a deliberate layout, with scrolling rather than compressed controls or hidden resource capabilities. |
| [NN/g: Progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | Keep frequent tasks visible and defer specialized choices. | Starting one resource needs no encoder, port or permission-policy configuration tour. Expert controls remain reachable. |
| [NN/g: Visual hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/) | Scale, contrast and grouping establish attention order. | Device identity is the main heading; resource names and clear states follow; configuration is secondary. Use a limited type scale, aligned controls and restrained color. |
| [NN/g: System status](https://www.nngroup.com/articles/visibility-system-status/) | Feedback should explain current state and the result of an action. | Distinguish connecting, requesting permission, active, stopping, failed, unavailable and unknown. Paired does not imply capturing. |

The direct Apple Layout page exposed only its JavaScript shell and an unsupported
Markdown content type through the research tool. The direct Material window-size
URL was unavailable. Claims above use the accessible Apple disclosure guidance
and Google's official Material 3 adaptive documentation, not those missing pages.
No complete review of every vendor's HIG is claimed.

## Nielsen Norman Group heuristic review

This is an independently authored application checklist derived from
[NN/g's ten usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/).
It is a proposed test oracle, not a completed user study.

| Focus | Blent review criterion |
| --- | --- |
| Status | Show connection and resource outcomes separately. |
| Familiarity | Name display, camera, microphone and speakers; hide backend jargon from routine tasks. |
| Control | Stop one resource; cancel pending requests; preserve unrelated sharing. |
| Consistency | Keep resource controls, labels and focus behavior predictable. |
| Prevention | Bind actions to exact device/resource identities; explain unavailable actions. |
| Recognition | Keep selected tablet, current resource state and relevant actions visible. |
| Efficiency | Offer keyboard access and retain safe preferences without restoring capture. |
| Focus | Remove persistent tuning, housekeeping paths and irrelevant Apply controls from home. |
| Recovery | Give a specific reason and next step at the failing resource. |
| Help | Put connection and consent guidance at the point of need. |

Guidelines differ in details. KDE's immediacy preference does not override Blent's
explicit Save/Start/restart contracts. GNOME's automation advice does not authorize
starting capture or accepting permissions. Native button spacing, input targets,
keyboard shortcuts and theming must suit the actual backend; mobile dimensions
or Apple chrome will not be copied blindly. Existing macOS and stylus exclusions
remain. A dark SVG is one visual sample, not a forced application theme.

## Revised concepts

All SVGs are static, simulated states. No Start/Stop control executes anything,
no preview captures a camera, and the sample connection/activity is not evidence
from a physical tablet.

- [Desktop resource workspace](artifacts/2026-10-26-t1268/resources-desktop.svg):
  select tablet, then use display/input, camera, microphone and speakers separately.
- [Compact resource workspace](artifacts/2026-10-26-t1268/resources-compact.svg):
  same resources in a single column; tablet selection replaces the persistent list.
- [First connection](artifacts/2026-10-26-t1268/resources-empty.svg):
  clear Connect action and a short explanation of available uses.
- [Camera approval pending](artifacts/2026-10-26-t1268/resources-approval.svg):
  tablet-side next step and Cancel request stay in the camera region; display
  and other resource states do not change.

The resource workspace has no permanent Apply bar. Configuration opens from its
resource and keeps Save/Discard with those edits. Save does not start media.
Display restarts are explicit when required. Disconnect belongs in connection
management and must disclose which resource owners it affects. Resource Stop
stays local. Do not add a misleading global Stop for one resource.

Camera settings preserve lens, resolution, frame rate, rotation, mirror,
background consent and bitrate/freshness controls. Audio preserves direction,
processing, buffer and background choices. Display/input preserves existing
modes, encoder/GPU/resolution/FPS and capacity controls. Optional controls are
organized by purpose; the redesign removes neither functionality nor tests.

## Contracts and acceptance before implementation

T1272 owns a proposed independent device/resource snapshot and action contract.
It must compose authoritative views from connection, display and media owners,
without copying mutable lifecycle state or treating labels as identity. Unknown
external activity must stay unknown. Existing controller capacity must remain
explicit: the mock does not promise a camera or audio session per tablet.

T1273 owns native UI composition after the owner selects a design and T1272 is
ready. Device selection must never replace or stop the previous resource owner.
Drafts stay bound to their exact target/resource. Pending commands keep their
original identity and outcome, including on navigation, cancellation and close.
Logical completion is not a native release fence. Preserve actual cleanup
sponsors, retained unknown obligations and explicit reuse evidence.

Review these flows before resuming production work:

1. Connect a tablet and choose only camera, microphone or speakers; no display
   Start is required by the UI.
2. Use two resources together and stop either without changing the other.
3. Deny or delay tablet approval; keep the next step and cancel/retry rules clear.
4. Switch tablets while a resource or command is active; keep ownership intact
   and show when capacity is occupied by another tablet.
5. Reconnect or lose the transport; distinguish stopping/unknown from confirmed
   cleanup and prevent replay to a replacement identity.
6. Edit one resource, change selection, and return; save to the original target
   or explicitly discard, without starting capture.
7. Exercise keyboard/screen-reader names, large text and narrow/short windows.
8. Show unsupported/preview backends truthfully and explain missing prerequisites
   per resource/transport. No new macOS or stylus work is authorized.

These are acceptance scenarios, not measured task-success or performance results.
The owner accepted the revised concepts; task walkthroughs remain implementation acceptance work. Static SVG
inspection cannot establish interaction accessibility or native resource safety.

## Display-control scope comparison (2026-10-27)

The approved resource workspace offered two display-scope choices. The former
`blent start`/`blent stop` control the entire display service; neither accepts
a tablet target. Camera, microphone and speakers already use independent target
contracts. A per-tablet display Stop must not be simulated by disconnecting the
whole tablet or stopping the service.

| Variant | Display action | Implementation consequence |
| --- | --- | --- |
| [A: global display controls](artifacts/2026-10-26-t1268/resources-global-display.svg) | Stop all display/input assignments, with scope explicitly labeled All tablets. | Reuses the current display-service backend; camera/audio still have separate controls. |
| [B: per-tablet display controls](artifacts/2026-10-26-t1268/resources-per-tablet-display.svg) | Stop only the selected tablet's display/input owner. | Requires a new target-bound display-control contract, native adapter and retirement regressions; preserves separate Disconnect and service controls. |

Both static comparisons show two simulated connected tablets and keep the same
resource layout. The owner requested both mockups before choosing this behavior;
the selected behavior is recorded below.

The owner selected variant B on 2026-10-27. T1274 implements the independent
per-tablet display-control backend; T1273 wires those actions into the UI.
Global display-service administration remains separate in Settings.
