# Blent UI/UX review — 2026-11-22

Review baseline: runtime commit `080d6546`, documentation checkpoint `0ca932e8`.
This is a heuristic review and improvement proposal, not an implemented redesign
or a usability study with participants. Findings are tracked individually in
`TODO.md` as T1780–T1792. No sharing controls, saved preferences, desktop settings,
or running processes were changed for this review.

## Evidence and limits

Inspected current desktop presentation, navigation, draft/save/close handling,
resource targeting, connection guidance, camera controls/preview, and Android
main/settings composition. Native screenshots establish Overview, General,
Cameras and Video appearance at 1040×740 on Cinnamon/X11. Reviewed Android
settings in source; its settings sheet was not exercised on the live tablet.
No native KDE/GNOME/Windows session, screen-reader session, 200% text trial,
error injection, or user task-completion study was performed. This review does
not establish complete accessibility or platform compliance.

The desktop reports GTK theme `Mint-Y-Aqua`, font `Ubuntu 10`, text scale `1.0`.
`gui/src/workspace_style.rs::configure` instead selects egui Light and fixed
proportional fonts, text colors and selection blue. Owner clarification during
review: “grey” meant **the operating system's standard light appearance**.
The earlier light-grey change only partially met that intent.

Screenshots remain local in `/tmp/blent-ux-review-20261122/`; do not treat that
path as a permanent artifact. Source-reproducible color measurements are retained
in [contrast.json](artifacts/2026-11-22-ui-ux/contrast.json). Ratios use sRGB relative
luminance and `(lighter + 0.05) / (darker + 0.05)`. The overview background sample
is RGB(248,248,248); foreground/selection and Android colors come from code.
Antialiased edge pixels are not used as intended foreground colors.

## Guidance applied

| Source | Relevant guidance | Application to Blent |
| --- | --- | --- |
| [KDE: Simple by default](https://develop.kde.org/hig/simple_by_default/) and [layout/navigation](https://develop.kde.org/hig/layout_and_nav/) | Familiar platform styling; expose common tasks, keep advanced capability available; give useful next actions. | Use native appearance inputs, preserve task-oriented resource cards, reduce service/engineering detail in everyday views. |
| [GNOME: UI styling](https://developer.gnome.org/hig/guidelines/ui-styling.html), [navigation](https://developer.gnome.org/hig/guidelines/navigation.html), [keyboard](https://developer.gnome.org/hig/guidelines/keyboard.html) | Standard styles with minimal custom styling, coherent view hierarchy and keyboard access. | Respect native light colors/fonts, expose parent navigation and test keyboard traversal. |
| [Microsoft: App settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings) | Separate everyday commands from preferences, group related settings, keep readable widths and reveal secondary options progressively. | Separate live resource controls from global preferences. Existing bounded form width is useful. This consultation does not resume Windows implementation. |
| [Google: Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility) and [Compose accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults) | Legible scalable text, sufficient contrast, meaningful semantics and usable touch targets. | Fix Android help contrast, retain standard Compose control semantics and validate large text. The existing settings gear already has a 48dp target and accessible description. |
| [Nielsen Norman Group: 10 usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | Visible state, familiar language, user control, consistent behavior, error prevention and recovery. | Explain draft scope, effects of saving, unsaved close behavior and available recovery steps. |
| [Laws of UX: Hick](https://lawsofux.com/hicks-law/), [Fitts](https://lawsofux.com/fittss-law/), [proximity](https://lawsofux.com/law-of-proximity/), [Jakob](https://lawsofux.com/jakobs-law/) | Choice complexity, target acquisition, grouping and learned expectations are useful design lenses. | Put camera adjustments beside the image, put Apply beside its affected controls, use familiar platform patterns. These are hypotheses to validate, not measured Blent speedups. |

Do not mechanically combine incompatible platform conventions. Desktop and tablet
should share task semantics, with appropriate native presentation. Blent's explicit
requirements take precedence: closing active media must preserve sharing, and
backward-compatibility interfaces must not be retained. KDE's generic close advice
and Jakob's familiar-version example do not override those decisions. Do not turn
every control into immediate apply: disruptive display restarts need explicit intent.

## Concrete screen direction

Keep **Tablets / Connections / Settings / About** initially: the structure is
already implemented and its immediate problems can be fixed without a wholesale
navigation rewrite. Clearly highlight the parent Settings tab on every child.
Keep **General** first inside Settings, as requested. Use a persistent context
line such as “Camera · RugKing Pad 2 Pro · USB debugging (ADB)” when the identity
and route are actually known. For global options say “Display preferences · all
tablets”; do not imply per-tablet settings that the model does not implement.

The Camera page should contain a compact state/action row, a large live preview,
and an adjacent Image section: shadow correction, exposure and anti-flicker with
capability-aware help. Session options such as lens/resolution belong in a distinct
section with a visible restart requirement. Advanced transport, bitrate and worker
controls remain available below. When stopped, the placeholder should say how to
start without taking most of the page. Preserve aspect ratio and the bounded
thumbnail/texture lifecycle; no second camera capture or full-resolution frame
retention is implied by this layout proposal.

Separate feedback into **Applied live**, **Unsaved preference**, and **Restart
required**. The exact backend acknowledgement remains authoritative: changing a
slider is not proof that the tablet applied it. Show the affected settings before
a global Save; if a field on another page is invalid, link to that field. Discard
must explicitly say whether it reverts a live adjustment as well as a saved draft.

Overview should keep resource cards and distinct state labels. Prefer a short
human-readable state with a Details explanation over repeating lifecycle caveats
on every card. For example, display assignment can be shown as “Display assigned”
with “Video delivery has not been verified” in its detail. Do not replace it with
“Streaming” unless an appropriate current observation exists.

## Native light-theme implementation boundary

The current egui `ThemePreference::System` selects light/dark from an optional
system theme value; it does not import GTK/KDE widget styling, palette or fonts.
Simply replacing `Light` with `System` would not fulfil the clarified request.
Evidence: installed egui 0.32.3 `memory/mod.rs::Options` / `memory/theme.rs`, plus
Blent's `workspace_style::configure`.

First prototype a narrow platform adapter supplying immutable semantic appearance
values to the existing presentation layer. It must not own camera state or mutate
the desktop theme. Define subscription lifetimes and unregister listeners when the
GUI context retires. Validate native light colors/font/scale and selection/focus
states on the actual environment; provide an explicit accessible default when a
capability is unavailable. That is current capability handling, not an old-version
compatibility shim.

An egui theme adapter can improve integration but does not turn egui controls into
native GTK/Qt widgets. If exact native control rendering is required beyond the
prototype's result, assess a native frontend behind the existing independent
contracts as a separate architectural decision. No toolkit migration is approved
or implemented by this report. Windows and macOS scope remains as already recorded.

## Dependencies and acceptance

1. T1786 appearance investigation informs T1780 semantic colors. T1780's existing
   contrast defect can be corrected independently rather than waiting for a toolkit
   decision. T1787 accessibility labels can proceed in parallel.
2. T1781 parent navigation precedes T1789 target context; use both for T1788 camera
   layout. T1790 route guidance reuses that context rather than duplicating identity.
3. T1782 draft scope precedes T1783 close behavior. Keep the original save/native
   owners authoritative. T1785 Android uses the same conceptual distinction while
   retaining its independent local/host protocol behavior.
4. T1784 Android readability is independent. T1791 feedback and T1792 General
   simplification reuse the established context and appearance rules.

Before marking behavioral fixes complete: permanent failing-before/passing-after
regressions, existing per-function coverage/complexity gates, and ownership review.
For UI acceptance, test default/minimum widths, 100/150/200% scale, keyboard-only
navigation, focused/selected/disabled/error states and long labels. Run Orca/AT-SPI
and TalkBack checks on their actual platforms; hosted semantic trees alone do not
establish screen-reader usability. Verify no visual reflow changes the admitted
resource or starts/stops sharing. Keep screenshots/logs free of camera imagery or
credentials unless separately authorized.

After implementation, validate task flows with users: connect a tablet, locate the
active camera, brighten the image, distinguish live/persistent/restart changes,
close/reopen without losing work, and recover from a failed start. Record completion,
errors and interruptions against the baseline. No claim of reduced time or support
burden is justified until those comparisons exist.
