# Broker activity verification — 2026-11-22

## T1771: admit inventory only when discovery is needed

An empty broker now avoids USB inventory helper admission. Discovery remains
needed when the authoritative controller contains any admitted client, saved peer
or live/retiring link. The Linux adapter reads that bounded state directly; it
does not allocate snapshots or maintain a duplicate demand flag. Remembered tablet
reconnect therefore remains active when the window is closed.

When demand disappears, the adapter marks its cached inventory unavailable and
makes the next scan immediately eligible. A returning client's first Inspect waits
for fresh metadata. An already admitted scan stays owned until both its original
async task and native helper have retired; demand loss never cancels that evidence
or admits an overlapping replacement. Device IDs remain monotonic, and no link,
route, pairing or native ownership is released by cache invalidation. The change
adds no allocation or retained resource; existing inventory bounds and cleanup
owners apply on success, failure, shutdown and caller loss.

A private broker with a synthetic inventory helper launched **three helper
processes in a 4,200-ms observation before the change, zero afterward**. The helper
itself records each execution. This finite empty-broker observation is neither
an active-link CPU result nor a tablet/battery claim. The outer 20-ms dispatcher
and active/remembered-peer scan interval remain unchanged in this increment.

Three permanent regressions failed before implementation: unnecessary admission,
stale idle inventory and the native helper-spawn observation. All pass afterward.
Six focused cases include all eight boolean demand combinations, returning UI
freshness, remembered-peer discovery and loss of the last client while a helper
is still owned. All 294 selected broker cases pass under LLVM instrumentation.
The exact executed host test object gives `Controller::inventory_needed` 3/3 and
`Server::scan` 19/19 executable lines covered. Rust 1.100.0, cargo-llvm-cov 0.8.7;
per-function counters are exported from that exact object rather than unrelated
objects present in the build cache. The repository Rust syn 2.0.119 checker
measures 64 functions across the changed source/test files, maximum complexity 7.

Evidence: `artifacts/2026-11-22-broker/t1771/`. No installed session, USB device,
user trust store or saved setting was touched. T1605 retains dispatcher/link
scheduling, snapshot overhead, configurable retained intervals and integration
acceptance through its independent children.

## T1776: suspend an empty broker's dispatcher timer

The dispatcher now polls its 20-ms interval only while controller discovery demand,
an admitted inventory owner or delayed accept recovery requires maintenance. Socket,
client/link, authority-worker and inventory readiness remain independently polled.
The guard reads authoritative state without allocation; it does not duplicate
lifecycle flags or release any native owner. A stopped client/link still remains
in the controller until its original retirement is observed, keeping maintenance
active. An admitted inventory also keeps observation active until it can be
collected. A pending overload exchange has its own readiness/deadline future.

A private empty broker produced **31 dispatcher waker notifications in 600 ms
before the change, zero afterward**. The permanent counter forwards every observed
wake to the original task. This measures dispatcher notifications, not total
process/kernel wakeups, CPU, active-link or tablet performance. A timer already
registered before demand disappears may deliver its last pending notification;
the idle dispatcher does not renew it. Active maintenance retains its existing
cadence in this increment.

The counted-wake regression fails before and passes after the change. Four focused
cases also verify that a later socket wakes the same running dispatcher and gets
fresh inventory, an accept error recovers with no admitted client, and saved peers
or an admitted helper keep maintenance enabled. All 298 selected broker cases
pass. Exact executed-object LLVM counters give `Server::run` 12/13 executable
lines (92.3%) and `maintenance_needed` 5/5 (100%). Rust 1.100.0 /
cargo-llvm-cov 0.8.7; the repository syn 2.0.119 checker measures 42 source/test
functions, maximum complexity 6. Evidence is in
`artifacts/2026-11-22-broker/t1776/`.

No new storage, native resource, detached callback or ownership handoff is added.
The existing interval belongs to the running dispatcher future and is dropped
with it. Readiness observations grant no release/reuse authority. Existing exact
client/link/helper settlement and bounded admission remain unchanged. All fixtures
use private sockets/state/helpers, close originals and drain authority/native
owners; no installed process or physical USB device participates. Active deadline
scheduling and readiness allocation remain T1777/T1778 under parent T1772.
